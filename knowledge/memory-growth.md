# 公開の版では、今の道具で測れない

- `window.__game`（`scene`・`buildings`・`debug.roads.warp` ほか）は `src/main.ts` の `if (import.meta.env.DEV)` の中で作られ、本番のビルドからは消える。`vite build` の出力に `__game` は 1 件も無い。[^m11-bundle]
- そのため `scripts/qa/memory-buildings.ts`（と `perf-buildings.ts` ほか `__game` を読む QA の道具）は、`vite preview` で配った公開の版では動かない（ゲームの準備待ちが 180 秒で切れ、近景の LRU を読む所で `ReferenceError`）。[^m11-bundle]
- `vite build --mode development` だけでは DEV にならない（出力に `__game` が無いまま）。`NODE_ENV=development` を付けると、DEV のまま束ねた版になる（`__game` あり）。[^m11-bundle]
- 公開の版に QA の読み口は足さない（設計の判断、2026-11-15。`__game` は車を置く・ワープする・内部を読む口で、遊ぶ人のコンソールからも呼べるようになるため）。計測の基準は、次の「DEV のまま束ねた版」にする。

## DEV のまま束ねた版（計測の基準）

- `just build-qa-bundle` で `dist-qa/` に束ね（`NODE_ENV=development vite build --mode development`）、`just serve-qa-bundle [port]` で `vite preview` で配る。
- 公開の版との違いは `import.meta.env.DEV` が真であることだけ。それで動くのは、`src/main.ts` の `__game` の塊（5590 行から）と `?inlineRoads`・`?noprewarm`、`src/i18n/index.ts` の検査、`src/assetsPage.ts` の分岐、ログの毎行の検査（`src/log.ts`）、`perf` の記録（`src/game/perf.ts`）。
- 束ねる設定（圧縮・target・入口）は同じ。ただし **チャンクの分け方は違う**: DEV の塊にある `import("./debug/viewHooks")`・`import("./debug/expresswayDrive")` のため、公開の版の 2 つ（main 6.7 MB・x-zone30plus 1.1 MB）が、DEV の版では main 2.3 MB・vehicle 4.4 MB・three.core 0.39 MB・x-zone30plus 0.68 MB などに分かれる（JS の合計はほぼ同じ）。どちらも圧縮されている。[^m11-bundle]

# ワープのせいではなく、場所が変わり続ける間に時間あたり一定で増える（指示の 1.2、2026-11-15）

QA の版、視界 far、20 分ずつ。5 分から終わりまでの最小二乗。[^m3-steps]

| 走り                     | ワープの回数 | 道のり                           | ヒープ MB/秒 | ヒープ MB/km | 配列の実体 MB/秒 | 近景の持っている量 |
| ------------------------ | ------------ | -------------------------------- | ------------ | ------------ | ---------------- | ------------------ |
| 輪・300 m・10 秒         | 110          | 33 km（一周 27.5 km を越える）   | 0.56         | 20.7         | 0.46             | 383 MB             |
| 輪・75 m・5 秒           | 220          | 16.5 km                          | 0.50         | 36.3         | 0.10             | 383 MB             |
| 輪・15 m・1 秒           | 1,078        | 16.2 km                          | 0.44         | 32.9         | 0.20             | 383 MB             |
| 往復 900 m・300 m・10 秒 | 112          | 33.6 km（同じ 900 m を 20 往復） | 0.49         | 17.9         | 0.06             | 261 MB（一定）     |

- **ワープの回数に比例しない**: 75 m と 15 m は同じ道のりでワープが 5 倍違うが、ヒープの増えは同じ程度（+488 / +483 MB）。
- **新しい場所を読む分でもない**: 往復は同じ 900 m を行き来し、近景の持っている量（261 MB）と配列の実体は横ばいなのに、ヒープは同じ速さ（0.49 MB/秒、ワープ 1 回あたり約 3.7 MB）で増え続けた。「場所ごとに 1 回作って捨てない物」ではない。
- 4 本で一番そろうのは時間あたり（0.44〜0.56 MB/秒）で、距離あたり（18〜36 MB/km）は 2 倍ばらつく。止まっていると増えない（タイトル画面、自動運転が止まった後）。**場所が変わり続ける間、時間あたり一定で溜まる物**が M1 の主な部分と読む（同じ場所に居続けると増えない）。ワープの走りでは、車はワープとワープの間は止まっているので、「車が動いている間」とは言えない（2026-11-16 に言い方を直した）。形が合うのは「場所が変わると入れ替わり、入れ替えの速さに上限がある物」（交通 AI・歩行者の出現など）だが、確かめていない。
- 配列の実体の増えは、新しい場所を読む輪の走りにだけあり（往復では 0.06 MB/秒）、ヒープとは別の物。
- 1 回ずつの計測。

# 何が溜まっているか（2026-11-16、途中）

## 数には出ない

往復 15 分で GC 後のヒープは 486 → 1,184 MB と増えたが、シーンの物（2,600〜3,700）、ジオメトリ（757〜885）、テクスチャ（222〜257）、剛体（32〜43）、コライダー（3,093〜3,996）、交通 AI の車（33〜34）、歩行者（25〜49）は、どれも往復の行きと帰りで上下するだけで、時間とともに増えなかった。違反の記録は 0 件のまま。[^m4-counts]

## 割り当ての標本: 描く物の控えと、人と車の模型

5〜15 分の間に作られ、15 分の時点で生きている物（ヒープは 455 → 789 MB と 469 → 803 MB、どちらも +334 MB）。[^m5-alloc]

- 上位は 2 回で同じだった。上の 3 行（描く物の控え、人、車）で約 340〜350 MB、ヒープの増え（334 MB）をほぼ全部説明する（標本からの見積もりなので、合計が増えより少し大きい）。
- 読み（コードを読んだだけで、ヒープのスナップショットの保持の経路では確かめていない）: three 0.186 の `RenderObjects` は、作った描く物の控えを `_renderObjects` という Set に持ち、物・材質・ジオメトリの `dispose` の知らせでだけ捨てる。歩行者は `scene` から外すときに共有でないジオメトリだけを `dispose` し（人の部品は `clone(true)` で共有のジオメトリ、材質も色ごとの共有）、交通の車は `scene` から外すだけ。だから場所が変わって入れ替わった人と車の、描く物の控えが残り、控えが模型を持ち続ける。入れ替えの速さには上限があるので、時間あたり一定になる。[^m5-three]
- 鏡の分があるのは、鏡もパスごとに別の控えを作るため（読み）。

## スナップショットは取れなかった

# 直し (a): 歩行者と交通の車を dispose する（2026-11-16）
