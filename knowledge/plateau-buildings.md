# 構成

- 都全域の集約 tileset（`13-bldg-lod1-latest`）を 3DTilesRendererJS 0.5.3 で読む。配信元は CORS `*`。中身は 3D Tiles 1.0 の b3dm で、Draco 圧縮と CESIUM_RTC を使っている。
- `LoadRegionPlugin` で読み込み範囲を絞る。
  - プレイヤーを中心とする半径 2.8km（スマホは 1.6km）の SphereRegion をマスクにする。
  - 半径 250m は全方向を最高詳細度で読む。車の背後にも衝突判定を作るため。
- 衝突判定は、見えているタイルのメッシュから Rapier の trimesh を作る。作るのは 100ms ごとに 1 個まで。
- LOD1 には色が無いため、窓・ブロックごとの色・夜の点灯はシェーダーで描く（`src/world/facade.ts`）。

# 遠くの街並み（2026-10-05 追加）

- 同じ集約 tileset をもう 1 つの TilesRenderer で、粗い階層（区ごとの大きい建物 20〜80 棟）だけ 14〜26 km まで読む。子を preprocessNode で刈るプラグイン（`pruneToCoarse`）で、細かい階層と、最初の中身がもう全詳細の台東区を読まない。簡略版の外壁、衝突判定・影なし、近景と重なる所は 0.1 % 奥に描く。
- 上位の階層の中身（港区の根は 20 棟・411 三角形・141 KB のうち batch table 108 KB）、区ごとの最初の geometricError（165〜1,003 m、台東区は 32〜64 m の葉）、プリセットごとのタイル数と通信量は [遠景](far-skyline.md)。

# 近景と遠景の LRU（2026-11-15、X0）

> **訂正**: 2026-10-05 に遠景（2 つ目の TilesRenderer）を足してから、近景の上限 `buildingCacheBytes`（PC 0.8 GB、スマホ 0.35 GB）は効いていなかった。上の表の「88 MB、表示タイル 68」は遠景より前の記録。

## 何が起きていたか

- 3d-tiles-renderer 0.5.3 では、すべての `TilesRenderer` が、モジュールに 1 つの `DEFAULT_LRU_CACHE` を `lruCache` に持って始まる（TilesRendererBase.js 479 行）。[^x0-lib]
- 近景と遠景が同じキャッシュを使い、後から作られる遠景が `FAR_CACHE`（64 MB・320 件、スマホ 24 MB）を書いて、近景の上限を上書きしていた。
- 結果、PC の既定（最高 = 視界 far）とスマホの既定で、近景の LRU が満杯になり、近くの建物が場所によって欠けていた。[^x0-points]
  - 例: 大田区の多摩川沿いで表示タイルが 1 件の回があった（直すと 132 件）。スマホの北区では 7〜24 件（直すと 33 件）。
  - 視界 near（半径 1.6 km）の PC では、江戸川区の 1 地点を除いて満杯にならず、絵は変わらない。

## 直し

- `giveOwnLru`（`src/world/buildings.ts`）で、近景と遠景のそれぞれに、`new TilesRenderer` の直後に新しい `LRUCache` を持たせる。解放の順序はライブラリの既定（`DEFAULT_LRU_CACHE.unloadPriorityCallback`）。ライブラリは「最初の `update()` の前なら替えてよい」としている。
- ダウンロードと解析の待ち行列は共有のまま（ページの通信を分け合うもので、「遠景は街の後」の順序もそれに依る）。
- テスト: 2 つの `lruCache` が別で、どちらも `DEFAULT_LRU_CACHE` でないこと。[^x0-test]

## 上限の決め方（使っている量の最大 × 2）

- ライブラリの LRU は、**使っている**タイル（直前の走査で要ると判定された物、`usedSet`）は捨てない。**使い終わった**タイルは、持っている量が下限（`minBytesSize`、上限の 0.6 倍）を超えた分だけ捨てる。だから走った後の持っている量は、ほぼ下限に張り付き、街が要る量を表さない。[^x0-lib]
- 上限は「使っている量（`usedSet` のバイトの合計）の最大 × 2」を 32 MiB 単位に切り上げた値にした。下限（1.2 倍）の内に使っている量が収まるので、使っているタイルが捨てられない。[^x0-warp]

| 設定                                                    | 使っている量の最大（どこで）               | 上限                        |
| ------------------------------------------------------- | ------------------------------------------ | --------------------------- |
| 視界 near（1.6 km）                                     | 111 MB（タイトル画面の回る視点）           | 224 MiB                     |
| 視界 medium（2.8 km）                                   | 204 MB（タイトル画面）                     | 416 MiB                     |
| 視界 far（4 km）                                        | 312 MB（ワープの 52 歩目、新宿と池袋の間） | 608 MiB                     |
| スマホの `?phoneTown=full`（半径は視界に依らず 1.6 km） | 130 MB（ワープ、池袋）                     | 256 MiB（試す値。既定は下） |

- **LRU の上限は、実際のメモリの上限ではない。** LRU が数える 1 MB は、配列の実体（タイルの頂点などの ArrayBuffer、`Runtime.getHeapUsage` の `backingStorageSize`）で約 4.4 MB、GC 後の JavaScript のヒープで約 1.6 MB、合わせて約 6 MB を使っていた（ヒープの上限 2 GB の試験の 20〜30 分で、配列の実体 ≈ 近景の持っている量 × 4.4 + 0.45 GB。下の節）。何がその 4.4 倍を持っているかは調べていない（M2: タイルごとの座標の写し、外壁の属性、読み込んだファイルの実体が残っている、などが候補）。調査の記録は [memory-growth.md](memory-growth.md)。GPU のメモリと物理（コライダー）のメモリは、この数字に入っていない。
- 使っている量は走りごとに 2 割近く違う（far のワープで 253〜312 MB）。決めた後の確かめは「使っている量の最大が下限以下なら確定」とした。
- **スマホは、実機で確かめてから決める（U12 の回答、2026-11-15）。** 軽い設定（`low`）は main の実効のまま: 近景の上限 24 MiB（`FAR_CACHE` のスマホの上限。2026-10-05 から実際に効いていた値）、建物の半径は視界の設定のとおり。近景と遠景の LRU が別になった分だけ、main より取り合いが無い。実機の結果と、端末の種類ごとの既定は下の「スマホの既定と見張り」。
- 試す値は URL の `?phoneTown=full` で選ぶ（スマホのときだけ効き、PC では無視。2026-11-16 から `?phoneTown=low` も読む。知らない値は既定）。上限 256 MiB、建物の半径は視界に依らず 1.6 km（視界に合わせてキャッシュを増やすと、スマホで far のときにヒープが PC と同じだけ増えるため。遠景・地形・写真は視界の設定に従う）。合計のメモリは、PC の Chrome でのスマホの設定で約 0.8〜0.9 GB から約 1.6〜1.9 GB になる見込み。
- `phoneTown` が付いているときだけ、画面の左上に 3 行を出す（`src/debug/phoneTownHud.ts`）: 経過時間、読み直しの回数（ページを読むたびに `localStorage` の `tod.phoneTown.<値>.loads` を 1 増やす。タブが落ちてブラウザが開き直すと増える。表示を長押しで 0 に戻す）、近景の表示タイル・持っている量と上限・満杯のフレーム。公開された版に引数を付けて実機で開き、端末の側でログを取らずに合否を読むため。引数は後の確かめにも使えるので残す。
- 止まっている地点の使っている量は、視界 far で 52〜157 MB。新宿・池袋のあたりを走ると 300 MB 前後まで行く。

## スマホの既定と見張り（2026-11-16、U12 の続き）

### 実機の結果と決定

- 2026-11-16、ユーザーが Pixel と iPhone の実機で、公開の版に `?phoneTown=full` を付けて約 25 分走らせた（新宿〜池袋の手順）。どちらも `reloads 0`・`full 0` のまま、落ちなかった。機種の細かい型番・OS とブラウザの版・走った道・終わりの時点のキャッシュの量・画面の写しは受け取っていない。[^phone-trial]
- 決定: **`full`（256 MiB・1.6 km）を、試した種類の端末にだけ既定にする。** 試していない種類は、試すまで `low`。0.8 km の中間の版は作らない（落ちなかったので要らない）。
- 種類は `src/device.ts` の `ANDROID_TOWN`・`IOS_TOWN`（iPhone と iPadOS。iPadOS 13 以降は UA が Macintosh なので、タッチ点の数で Mac と分ける）。Android でも iOS でもないタッチ端末は試していないので `low`。
  - **2026-11-16 から、どちらも `full`。** 根拠は、Pixel と iPhone の両方で上の確かめが通ったこと（ユーザーの答え）。
- 引数があれば既定より優先（`full`・`low`）。左上の試しの表示は、引数が付いたときだけ出す。

### 県境の合計

- `full` のキャッシュが下限（161 MB）に着いた状態の合計（GC 後のヒープ + 配列の実体）は 1.4〜1.7 GB（PC の Chrome をスマホの設定にした計測。上の「県境のワープ」）。県境では 5 分ほどで着き、都心でも長く走れば着く。
- 実機の 25 分がその状態まで行ったかは分からない。加えて M1 の伸び（スマホの設定で 0.13〜0.17 MB/秒、1 時間で約 0.5〜0.6 GB）があるので、**実機の 25 分は 1 時間の走りを保証しない。** そのため、落ちた端末を戻す見張りを付けた。

### 見張り（`src/phoneTownWatch.ts`）

- `localStorage` の `tod.phoneTown.watch` に `{ run, demoted }` を持つ。`run` は、`full` の回が「表に出ている（`front`）」「裏に回った（`back`）」「きちんと終わった（`closed`）」のどれか。
  - 開いたとき（`device.ts` の読み込み時、重い読み込みの前）に `front`。`visibilitychange` で `back` / `front`、`pagehide` で `closed`、back/forward キャッシュから戻った `pageshow` で `front`。
- 開いたとき、前の回が `front` のまま（表に出たまま、どの出来事も無く終わった）なら、メモリで落ちた疑いとして 1 回数える。**1 回で `low` に戻し、覚える**（`demoted`）。その回の最初の走り出しで 1 回だけ知らせる（i18n `toast.phoneTownReduced`、3 言語）。
  - 裏に回ってから終わった回（アプリの切り替え、OS が裏のタブを片付けた）、閉じた回、読み直し・別のページへの移動は数えない。
  - `?phoneTown=full` で開くと、覚えを消して `full` に戻る。
  - 保存が使えないとき（プライベートのタブ、サイトのデータの拒否、書けないとき）は `low`。覚えられないので、落ち続けるのを防げないため。
  - `low` の回は見張らない（`run` を空にする）。戻る先が無く、後で `full` になったときに古い `front` を数えないため。
- 決め方は純粋な関数（`openWatch`・`runAfter`）で、テストがある。開いたときの結果はログ `phone_town_chosen`（kind・town・reason・param・crashed・demotedNow）。[^phone-watch-test]
- Why not `navigator.deviceMemory` で分ける: Android の Chrome にしか無く、iPhone では読めない。Why not 2 回落ちてから戻す: 1 回目で遊べなくなっている。誤って戻しても失うのは建物の量だけ。
- 試しの表示（`phoneTownHud.ts`）は、保存が使えないとき `reloads ?` と出す（前は数えていないのに `reloads 0` と読めた。PR #91 のレビューの Minor）。

### 確かめ（ヘッドレス Chrome、Android の UA）

`ANDROID_TOWN` を手元だけ一時的に `full` にした開発サーバー（既定を `full` にする前の版。見張りの中身は同じ）で、1 つのプロファイル（同じ `localStorage`）のまま順に開いた。[^phone-watch-crash]

| 手順                                                                              | 近景の上限           | 理由（reason）                    |
| --------------------------------------------------------------------------------- | -------------------- | --------------------------------- |
| 引数なしで開く                                                                    | 256 MiB・半径 1.6 km | default                           |
| `Page.crash` で落とし、開き直す                                                   | 24 MiB               | demoted（走り出しで知らせが出た） |
| もう一度開き直す                                                                  | 24 MiB               | demoted（知らせなし）             |
| `?phoneTown=full` で開く                                                          | 256 MiB              | param（覚えが消えた）             |
| 引数なしで開く → 読み直す                                                         | 256 MiB              | default                           |
| 別のタブを前に出し（`hidden`、`run` は `back`）、裏のまま `Page.crash` → 開き直す | 256 MiB              | default（数えない）               |
| 別のタブへ移ってから閉じる → 別のタブで開く                                       | 256 MiB              | default                           |
| 表に出たまま閉じる → 別のタブで開く                                               | 256 MiB              | default                           |
| 表に出たまま `Page.crash` → 開き直す                                              | 24 MiB               | demoted                           |

### 確かめていないこと

- Pixel・iPhone 以外の機種（メモリの少ない Android、古い iPhone）。OS とブラウザの版。走った道。終わりの時点のキャッシュの量。実機での合計のメモリ。県境を実機で走った結果。1 時間を超える走り。
- iPhone の Safari が、メモリでタブを落とすときに `visibilitychange` や `pagehide` を出さないこと（出すなら、見張りは数えない）。`Page.crash` の確かめは Chrome だけ。
- 見張りの誤り（表に出たまま、メモリ以外の理由で終わる回: 電池切れ、ブラウザごと強制終了された、など）がどれだけあるか。
- 同じ端末でゲームを 2 つのタブに開いたとき（後から開いたタブが前のタブの `front` を読むと、落ちていなくても数える。前のタブは、後のタブが前に出た時点で `back` を書くはずだが、確かめていない）。
- 実機の確かめ（マージの後、引数なしで開いて建物が出ていること）はまだ。

## main に前からある増え（M1、未解決）

- main で、近景の LRU が一定（64 MB）のまま、ワープの間に強制 GC 後のヒープが増え続ける（far で約 0.6 MB/秒、20 分で 0.3 → 1.0 GB）。止まっているタイトル画面では増えない。何が溜まっているかは調べていない（別の調査）。[^x0-warp] 調査の記録は [memory-growth.md](memory-growth.md)（開発サーバーの物ではないことまで確かめた）。

## 測り方の落とし穴

- **GC の前のヒープで比べない。** 同じ地点の 3 回で 868〜1,223 MB と揺れ、GC 後は 241〜244 MB。前回「LRU 1 MB あたりヒープ 8〜14 MB」と読んだのは、大半が回収前のごみだった。`HeapProfiler.collectGarbage` の後に `Runtime.getHeapUsage` で読む。

## 構成：根を 1 つ足し、レンダラーは 1 つのまま

- `public/data/plateau/tileset.json`（`just make-plateau-root`、`scripts/plateauRoot.ts`）が 4 都県の根を子に持つ。`PLATEAU_TILESET` はこれを指す。近景と遠景の `TilesRenderer` は、今までどおり URL を 1 つ受け取る。
  - 子の箱は `src/config.ts` の `PLATEAU_SOURCES`（余白込みの外枠）。読むかどうかは箱でなく門で決める（下）。
  - 根に内容は無い。子の `geometricError` は県の根と同じ 50000、`refine` は ADD。
- Why not 県ごとにレンダラーを 4 つ: LRU が県ごとに分かれて県境でメモリが最大 4 倍になり、load-model・dispose-model・切り抜き・コライダーの配線も 4 重になる。
- Why not 市の `tileset.json` を自作の根に並べる: 市の URL は `-latest` の更新で変わる。安定しているのは県の URL だけ。
- 3d-tiles-renderer 0.5.3 は、内容の無い根の下で `tileset.json` を指す子を 2 段続けてたどった。川崎駅で川崎区の建物のタイルが 111 件読まれたことで確かめた。[^load-measure]
- 遠景の刈り込み（`pruneTree`）は直していない。`json` を指す段では `depthFromRenderedParent` が増えないので、1 段深くなっても結果は同じ（テストで確かめた）。[^gate-tests]

## 門：他県の根は、近景の球がその県の市に掛かるときだけ読む

- 東京以外の子は `extras.gate` を持つ。中身は、生成のときにその県の根から写した、市ごとの `boundingVolume.region` の一覧。神奈川 33・埼玉 58・千葉 6 件。
- `src/world/buildings.ts` の `GatedSphereRegion` は `SphereRegion` を継ぐ。門のあるタイルは、球が箱に掛かるだけでは通さない。門の範囲のどれかに球が掛かることを求める。
  - 当たりの計算はライブラリと同じにした（`EllipsoidRegion` の外接箱を OBB にして `intersectsSphere`）。門が開くのは、その市が読み込みの対象になるときと一致する。
- 近景（`maskRegion`）は自分の球で門を判定する。遠景（`farRegion`）は近景の球で判定する。門を通った県の中では、遠景の球で市を選ぶ。
- Why 門（箱だけでは足りない）
  - 遠景の球（14〜26 km）は東京駅から埼玉・千葉の市に届く。門の前は、県の根 3 つと市の `tileset.json` 17 件（2.6 MB）を東京駅で読んでいた。[^load-measure]
  - 箱は県の形でない。神奈川の根の北の縁 35.672（相模原の北端）は、東京駅の 1.0 km 南にある。
- 東京駅では、近景の半径 3 つ（1,600・2,800・4,000 m）のどれでも 3 県が閉じる。旧江戸川沿いで千葉が閉じ、川崎駅で神奈川、川口駅で埼玉が開く（テスト 5）。[^gate-tests]
- 見え方: 他県の遠景は、近景の球がその県の市の箱に掛かるまで出ない。都心から川崎やさいたまの高層は見えない。門が閉じると、その県の遠景は一度に消える。開閉の回数は少ない（レビューの概算。同梱の門の箱までの距離で数えたもので OBB ではない。半径 1,600・2,800・4,000 m で、環八の羽田→砧 0〜1 回、環七の板橋→足立 0〜3 回、中央環状の板橋→葛西 1〜2 回）。
- 門は県の根の写しなので古くなる。新しく加わった市は、作り直すまで読まれない。`just check-plateau-root` が、今の県の根の範囲の集合と同梱の門を比べ、違えば終了コード 1 にする。

# なぜ LOD2 ではないのか

| 観点                            | LOD2（テクスチャ）                               | LOD1                |
| ------------------------------- | ------------------------------------------------ | ------------------- |
| 収録自治体（集約 tileset の子） | 45                                               | 62                  |
| 丸の内でのキャッシュ使用量      | 1,718MB で満杯、表示タイル 5                     | 88MB、表示タイル 68 |
| 中間階層                        | 簡略化された壁の断片が宙に浮く[^chiyoda-tileset] | 問題なし            |

`13-bldg-lod2-latest` と `13-bldg-lod2-texture-latest` は同じ子 tileset を指していて、テクスチャ無しの LOD2 は存在しなかった。[^headless-lru]

# 効かなかったこと

1. **LRU を 0.4GB → 1.0GB に上げる**: 期待したのは近くの詳細タイルが読めるようになること。実際は 104 タイル・1,081MB で満杯のまま、表示は 5 タイルだった。テクスチャ付き LOD2 は 1 タイルあたり約 10MB あった。
2. **LOD2 を `errorTarget: 2`・半径 1.1km・LRU 1.6GB にする**: 1,718MB で再び満杯になり、表示は 5 タイルのままだった。
3. 当初の真因は「都全域の tileset が遠くの区の粗いタイルまで読み、0.4GB の LRU を埋めていた」ことだった。マスク領域で範囲を絞り、LOD1 に替えて解決した。

## 浮いた板の原因 — **最初の診断は誤りだった（2026-10-04 追記）**

> **訂正**: 「メッシュのワールド座標の範囲が ±1.8km に広がっているので、Y-up→Z-up の変換が誤り、建物が倒れている」と考えたが、間違いだった。傾いた面の**軸平行の外接箱（AABB）を変換した 8 頂点の範囲**を測っていたため、範囲が水増しされていた。法線（屋根で ECEF の上方向を向く）を確かめて、向きは正しいと分かった。
>
> 本当の原因は LOD2 の中間階層（深さ 2〜4、geometricError 約 415）に入っている簡略化メッシュで、キャッシュ枯渇で最下層まで詳細化できず、それが表示され続けていた。

# 外壁テクスチャ（2026-10-04 追加）

- LOD1 のタイルのメッシュは複数の建物をまとめたもので、建物 ID の頂点属性を持つ。丸の内では 68 メッシュ中 63 が `_batchid`、5 が `_feature_id_0`（EXT_mesh_features 形式）だった。
- `load-model` の時点ではタイルはまだグループに入っておらず、`updateMatrixWorld` すると頂点が ECEF で得られる。タイル中心の放射方向を「上」として建物ごとの高さを求め、高さで外壁の種類を選ぶ。12m 以下はアパート・雑居ビル・倉庫・レンガ、30m 以下はマンション・雑居ビル・タイル張り、60m 以下はコンクリート・タイルのオフィスとマンション、それより高いとガラスかコンクリートのオフィス。階は建物ごとの基部から数える（頂点属性 `facade`）。
- 外壁 8 種類（agy が手続き生成、1 枚 = 幅 12.8m × 高さ 14m）を、色を RGB・窓マスクを A にまとめて 1 枚のテクスチャ配列にした。スマホは半分の解像度（2.3MB）。
- 浮動原点の付け替えで模様がずれないよう、水平方向の周期 PERIOD を 12.8m の倍数（576m）にした。
