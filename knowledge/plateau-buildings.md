# 構成

- 都全域の集約 tileset（`13-bldg-lod1-latest`）を 3DTilesRendererJS 0.5.3 で読む。配信元は CORS `*`。中身は 3D Tiles 1.0 の b3dm で、Draco 圧縮と CESIUM_RTC を使っている。
- `LoadRegionPlugin` で読み込み範囲を絞る。
  - プレイヤーを中心とする半径 2.8km（スマホは 1.6km）の SphereRegion をマスクにする。
  - 半径 250m は全方向を最高詳細度で読む。車の背後にも衝突判定を作るため。
- 衝突判定は、見えているタイルのメッシュから Rapier の trimesh を作る。作るのは 100ms ごとに 1 個まで。
- LOD1 には色が無いため、窓・ブロックごとの色・夜の点灯はシェーダーで描く（`src/world/facade.ts`）。

# 遠くの街並み（2026-10-05 追加）

- 同じ集約 tileset をもう 1 つの TilesRenderer で、粗い階層（区ごとの大きい建物 20〜80 棟）だけ 14〜26 km まで読む。子を preprocessNode で刈るプラグイン（`pruneToCoarse`）で、細かい階層と、最初の中身がもう全詳細の台東区を読まない。簡略版の外壁、衝突判定・影なし、近景と重なる所は 0.1 % 奥に描く。
- 上位の階層の中身（港区の根は 20 棟・411 三角形・141 KB のうち batch table 108 KB）、区ごとの最初の geometricError（165〜1,003 m、台東区は 32〜64 m の葉）、プリセットごとのタイル数と通信量は [遠景](far-skyline.md)。

# 近景と遠景の LRU（2026-11-15、X0）

> **訂正**: 2026-10-05 に遠景（2 つ目の TilesRenderer）を足してから、近景の上限 `buildingCacheBytes`（PC 0.8 GB、スマホ 0.35 GB）は効いていなかった。上の表の「88 MB、表示タイル 68」は遠景より前の記録。

## 何が起きていたか

- 3d-tiles-renderer 0.5.3 では、すべての `TilesRenderer` が、モジュールに 1 つの `DEFAULT_LRU_CACHE` を `lruCache` に持って始まる（TilesRendererBase.js 479 行）。[^x0-lib]
- 近景と遠景が同じキャッシュを使い、後から作られる遠景が `FAR_CACHE`（64 MB・320 件、スマホ 24 MB）を書いて、近景の上限を上書きしていた。
- 結果、PC の既定（最高 = 視界 far）とスマホの既定で、近景の LRU が満杯になり、近くの建物が場所によって欠けていた。[^x0-points]
  - 例: 大田区の多摩川沿いで表示タイルが 1 件の回があった（直すと 132 件）。スマホの北区では 7〜24 件（直すと 33 件）。
  - 視界 near（半径 1.6 km）の PC では、江戸川区の 1 地点を除いて満杯にならず、絵は変わらない。

## 直し

- `giveOwnLru`（`src/world/buildings.ts`）で、近景と遠景のそれぞれに、`new TilesRenderer` の直後に新しい `LRUCache` を持たせる。解放の順序はライブラリの既定（`DEFAULT_LRU_CACHE.unloadPriorityCallback`）。ライブラリは「最初の `update()` の前なら替えてよい」としている。
- ダウンロードと解析の待ち行列は共有のまま（ページの通信を分け合うもので、「遠景は街の後」の順序もそれに依る）。
- テスト: 2 つの `lruCache` が別で、どちらも `DEFAULT_LRU_CACHE` でないこと。[^x0-test]

## 上限の決め方（使っている量の最大 × 2）

- ライブラリの LRU は、**使っている**タイル（直前の走査で要ると判定された物、`usedSet`）は捨てない。**使い終わった**タイルは、持っている量が下限（`minBytesSize`、上限の 0.6 倍）を超えた分だけ捨てる。だから走った後の持っている量は、ほぼ下限に張り付き、街が要る量を表さない。[^x0-lib]
- 上限は「使っている量（`usedSet` のバイトの合計）の最大 × 2」を 32 MiB 単位に切り上げた値にした。下限（1.2 倍）の内に使っている量が収まるので、使っているタイルが捨てられない。[^x0-warp]

| 設定                                                    | 使っている量の最大（どこで）               | 上限                        |
| ------------------------------------------------------- | ------------------------------------------ | --------------------------- |
| 視界 near（1.6 km）                                     | 111 MB（タイトル画面の回る視点）           | 224 MiB                     |
| 視界 medium（2.8 km）                                   | 204 MB（タイトル画面）                     | 416 MiB                     |
| 視界 far（4 km）                                        | 312 MB（ワープの 52 歩目、新宿と池袋の間） | 608 MiB                     |
| スマホの `?phoneTown=full`（半径は視界に依らず 1.6 km） | 130 MB（ワープ、池袋）                     | 256 MiB（試す値。既定は下） |

- **LRU の上限は、実際のメモリの上限ではない。** LRU が数える 1 MB は、配列の実体（タイルの頂点などの ArrayBuffer、`Runtime.getHeapUsage` の `backingStorageSize`）で約 4.4 MB、GC 後の JavaScript のヒープで約 1.6 MB、合わせて約 6 MB を使っていた（ヒープの上限 2 GB の試験の 20〜30 分で、配列の実体 ≈ 近景の持っている量 × 4.4 + 0.45 GB。下の節）。何がその 4.4 倍を持っているかは調べていない（M2: タイルごとの座標の写し、外壁の属性、読み込んだファイルの実体が残っている、などが候補）。GPU のメモリと物理（コライダー）のメモリは、この数字に入っていない。
- 使っている量は走りごとに 2 割近く違う（far のワープで 253〜312 MB）。決めた後の確かめは「使っている量の最大が下限以下なら確定」とした。
- **スマホは、実機で確かめてから決める（U12 の回答、2026-11-15）。それまで既定は main の実効のまま**: 近景の上限 24 MiB（`FAR_CACHE` のスマホの上限。2026-10-05 から実際に効いていた値）、建物の半径は視界の設定のとおり。近景と遠景の LRU が別になった分だけ、main より取り合いが無い。
- 試す値は URL の `?phoneTown=full` で選ぶ（スマホのときだけ効き、PC では無視。値は `full` だけで、知らない値は既定）。上限 256 MiB、建物の半径は視界に依らず 1.6 km（視界に合わせてキャッシュを増やすと、スマホで far のときにヒープが PC と同じだけ増えるため。遠景・地形・写真は視界の設定に従う）。合計のメモリは、PC の Chrome でのスマホの設定で約 0.8〜0.9 GB から約 1.6〜1.9 GB になる見込み。
- `phoneTown` が付いているときだけ、画面の左上に 3 行を出す（`src/debug/phoneTownHud.ts`）: 経過時間、読み直しの回数（ページを読むたびに `localStorage` の `tod.phoneTown.<値>.loads` を 1 増やす。タブが落ちてブラウザが開き直すと増える。表示を長押しで 0 に戻す）、近景の表示タイル・持っている量と上限・満杯のフレーム。公開された版に引数を付けて実機で開き、端末の側でログを取らずに合否を読むため。引数は後の確かめにも使えるので残す。
- 止まっている地点の使っている量は、視界 far で 52〜157 MB。新宿・池袋のあたりを走ると 300 MB 前後まで行く。

## 決めた上限での量（ヘッドレス、強制 GC の後）

- 止まっている地点（視界 far）のヒープ: main 241〜320 MB に対し、X0 は 303〜608 MB。満杯 0、落ち着いた後の破棄 0。同じ絵の地点（main が満杯でない所）では、フレーム間隔の p95 は 3 回とも悪くはならなかった。[^x0-points]
- ワープ 20 分（3 回ずつ）の、X0 − main の GC 後の JavaScript のヒープの差の中央値は、far で約 +636 MB、スマホで約 +272 MB（ヒープだけの数字。配列の実体を足した合計の増えは、下の 2 GB の試験の節で far 約 +1.5〜2 GB、スマホ約 +1 GB）（近景の持っている量が横ばいになった後、同じ歩数の点どうし）。傾きは X0 の方が小さかった（far で X0 0.53〜0.59 MB/秒、main 0.59〜0.60 MB/秒）。X0 は main に無い増えを足していない。[^x0-warp]
- GC 前のヒープの最大は、far のワープで main 2.6〜2.8 GB、X0 4.4〜4.6 GB。回収前のごみが多い。
- ウィンドウを出した Chrome（GPU で描く、`--headed`）で視界 far の 1 回ずつ、フレーム間隔の p50/p95 は、東京駅 main 33.3/35.1 ms・X0 33.0/35.1 ms、大田区 33.3/50.0・33.4/50.4、川口駅 18.7/34.5・32.6/34.7（表示タイル 52 → 87）。p95 はほぼ同じで、川口駅の p50 だけ描く量の分だけ重い。
- 視点表 `landmarks`・`roads` の画素の差は、main どうしを 2 回撮った差（最大 4.7 % の画素）と同じ程度で、建物による差は見分けられなかった。
- タイトル画面（far）は、2 周目に 318 件の読み直しがあるが、満杯 0 で、同じ向きのコマを 0.8 GB の版と比べても建物の欠けは見えなかった。

## JavaScript のヒープの上限を 2 GB にしたとき（2026-11-15）

メモリの少ない機械のタブを真似て、Chrome を `--js-flags=--max-old-space-size=2048` で起動し、ワープの輪を 30 分走らせた（main と X0 を同時に 1 本ずつ。2 本目の組はスマホの main・X0 と X0 の medium の 3 本を同時に）。[^x0-warp]

| 走り         | タブ     | GC 後のヒープの最大（30 分の時点） | 20〜30 分の傾き | 配列の実体（backingStorage）の最大 | GC 前の最大 | 使っている量の最大 / 下限 | 満杯のフレーム       |
| ------------ | -------- | ---------------------------------- | --------------- | ---------------------------------- | ----------- | ------------------------- | -------------------- |
| main・far    | 落ちない | 1,311 MB（1,311）                  | 0.62 MB/秒      | 924 MB                             | 2.5 GB      | 71 MB（上限 67 MB）       | 30,328（ずっと満杯） |
| X0・far      | 落ちない | 1,512 MB（1,472）                  | 0.14 MB/秒      | 2,507 MB                           | 3.9 GB      | 299 / 382 MB              | 0                    |
| main・スマホ | 落ちない | 502 MB（488）                      | 0.18 MB/秒      | 400 MB                             | 1.4 GB      | 29 MB（上限 25 MB）       | 77,558（ずっと満杯） |
| X0・スマホ   | 落ちない | 832 MB（816）                      | 0.28 MB/秒      | 1,218 MB                           | 2.3 GB      | 130 / 161 MB              | 0                    |
| X0・medium   | 落ちない | 1,672 MB（1,672）                  | 0.62 MB/秒      | 1,938 MB                           | 3.4 GB      | 192 / 262 MB              | 0                    |

- 30 分では、どれも落ちなかった。上限に掛かるのは GC 後のヒープ（old space）で、タイルの頂点などの配列の実体（backingStorage、X0 の far で 2.5 GB）はその外にある。
- 20〜30 分の傾きのままなら、2 GB に届くのは、30 分の時点から main の far で約 20 分後（走り始めから約 50 分）、X0 の medium で約 10 分後（約 40 分）、X0 の far で約 67 分後（約 97 分）（上限の近くで GC が強くなり、傾きが寝た可能性がある。確かめていない）。

メモリの合計（GC 後のヒープ + 配列の実体。20〜30 分の、10 秒ごとの点の最小〜最大）:

| 走り         | JavaScript のヒープ | 配列の実体    | 合計          | 近景の持っている量 |

## 構成：根を 1 つ足し、レンダラーは 1 つのまま

- `public/data/plateau/tileset.json`（`just make-plateau-root`、`scripts/plateauRoot.ts`）が 4 都県の根を子に持つ。`PLATEAU_TILESET` はこれを指す。近景と遠景の `TilesRenderer` は、今までどおり URL を 1 つ受け取る。

- Why not 県ごとにレンダラーを 4 つ: LRU が県ごとに分かれて県境でメモリが最大 4 倍になり、load-model・dispose-model・切り抜き・コライダーの配線も 4 重になる。
- Why not 市の `tileset.json` を自作の根に並べる: 市の URL は `-latest` の更新で変わる。安定しているのは県の URL だけ。
- 3d-tiles-renderer 0.5.3 は、内容の無い根の下で `tileset.json` を指す子を 2 段続けてたどった。川崎駅で川崎区の建物のタイルが 111 件読まれたことで確かめた。[^load-measure]

- 撮影ラウンド 1 で、川崎駅の昼・川口駅の昼夜に近景の街並みが抜けたまま撮られた（`settled.isSettled` true、`buildingsProgress` 1）。[^x1-timeline]
- 時系列（地点 a・e・f、2 回ずつ、100 ms ごと）: `isSettled` が true になった時点で、近景の renderer は `loadProgress` 1・`isLoading` false・`queued` 0 なのに、`stats.downloading` が 4〜96 件残っていた（a 4・30、e 37・87、f 91・96）。最後の `load-model` は settled の後、a で 2〜3.5 秒、e で 5〜8 秒、f で 13〜14 秒後。`failed`・`refused` は全回 0。
- 仕組み（3d-tiles-renderer 0.5.3 のコードで確かめた）: ダウンロードの待ち行列の仕事は `fetch` の応答のヘッダーが届いた時点で終わり、本体（`arrayBuffer()`）は待ち行列の外で読まれる。本体の受信中に `downloadQueue.running` が false になり、`isLoading = false`・`inCacheSinceLoad = 0` となって `loadProgress` は分母 0 で 1.0 を返す。`stats.downloading` は本体の到着まで減らない（TilesRendererBase.js 393〜399・925〜932・1661〜1720 行）。
- 読み込み画面が閉じた時点（state が ready）で、自車から 300 m 以内の近景タイルは最終の a 0/2・e 2/7・f 1/5 しか出ていなかった。東京駅でも起きている、X1 の前からの不具合。
- 門のある県が遅れて読み始めることは無かった（最初の近景タイル: e は神奈川 1.85〜1.89 秒・東京 1.85〜2.08 秒、f は埼玉 2.00〜2.03 秒・東京 1.85〜1.89 秒）。
- X1 では直さない（設計の判断）。`Buildings.loadProgress()`・`farLoadProgress()` を `stats` の `queued + downloading + parsing` から出す直しを、main への別の PR（B1）にする。ワープの着地と全部の視点表の撮影にも同じ穴がある。
- X1 の撮影は、`scripts/qa/quietWatch.ts` の `waitQuiet` で待つ: 近景・遠景とも `load-model`・`dispose-model` が無く、`queued + downloading + parsing` が 0 の状態が 5 秒続くこと（視点表の `defaults.quietS`、`buildings-outside` だけ 5、ほかは 0）。`perf-buildings.ts` も同じ関数で待つ。

### 地点 e の遠景が読む東京の市の `tileset.json`

# なぜ LOD2 ではないのか

| 観点                            | LOD2（テクスチャ）                               | LOD1                |
| ------------------------------- | ------------------------------------------------ | ------------------- |
| 収録自治体（集約 tileset の子） | 45                                               | 62                  |
| 丸の内でのキャッシュ使用量      | 1,718MB で満杯、表示タイル 5                     | 88MB、表示タイル 68 |
| 中間階層                        | 簡略化された壁の断片が宙に浮く[^chiyoda-tileset] | 問題なし            |

`13-bldg-lod2-latest` と `13-bldg-lod2-texture-latest` は同じ子 tileset を指していて、テクスチャ無しの LOD2 は存在しなかった。[^headless-lru]

# 効かなかったこと

1. **LRU を 0.4GB → 1.0GB に上げる**: 期待したのは近くの詳細タイルが読めるようになること。実際は 104 タイル・1,081MB で満杯のまま、表示は 5 タイルだった。テクスチャ付き LOD2 は 1 タイルあたり約 10MB あった。
2. **LOD2 を `errorTarget: 2`・半径 1.1km・LRU 1.6GB にする**: 1,718MB で再び満杯になり、表示は 5 タイルのままだった。
3. 当初の真因は「都全域の tileset が遠くの区の粗いタイルまで読み、0.4GB の LRU を埋めていた」ことだった。マスク領域で範囲を絞り、LOD1 に替えて解決した。

## 浮いた板の原因 — **最初の診断は誤りだった（2026-10-04 追記）**

> **訂正**: 「メッシュのワールド座標の範囲が ±1.8km に広がっているので、Y-up→Z-up の変換が誤り、建物が倒れている」と考えたが、間違いだった。傾いた面の**軸平行の外接箱（AABB）を変換した 8 頂点の範囲**を測っていたため、範囲が水増しされていた。法線（屋根で ECEF の上方向を向く）を確かめて、向きは正しいと分かった。
>
> 本当の原因は LOD2 の中間階層（深さ 2〜4、geometricError 約 415）に入っている簡略化メッシュで、キャッシュ枯渇で最下層まで詳細化できず、それが表示され続けていた。

# 外壁テクスチャ（2026-10-04 追加）

- LOD1 のタイルのメッシュは複数の建物をまとめたもので、建物 ID の頂点属性を持つ。丸の内では 68 メッシュ中 63 が `_batchid`、5 が `_feature_id_0`（EXT_mesh_features 形式）だった。
- `load-model` の時点ではタイルはまだグループに入っておらず、`updateMatrixWorld` すると頂点が ECEF で得られる。タイル中心の放射方向を「上」として建物ごとの高さを求め、高さで外壁の種類を選ぶ。12m 以下はアパート・雑居ビル・倉庫・レンガ、30m 以下はマンション・雑居ビル・タイル張り、60m 以下はコンクリート・タイルのオフィスとマンション、それより高いとガラスかコンクリートのオフィス。階は建物ごとの基部から数える（頂点属性 `facade`）。
- 外壁 8 種類（agy が手続き生成、1 枚 = 幅 12.8m × 高さ 14m）を、色を RGB・窓マスクを A にまとめて 1 枚のテクスチャ配列にした。スマホは半分の解像度（2.3MB）。
- 浮動原点の付け替えで模様がずれないよう、水平方向の周期 PERIOD を 12.8m の倍数（576m）にした。
