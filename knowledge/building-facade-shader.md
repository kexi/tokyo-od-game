# 構成

`src/world/facade.ts` の 1 つのマテリアルだけで描く。描画呼び出し・頂点・テクスチャ取得（1 回）は変えていない。[^session-shots] main（WebGL）では MeshStandardMaterial の onBeforeCompile で GLSL を差し込み、webgpu ブランチでは同じ計算を TSL で書いた MeshStandardNodeMaterial（`FacadeMaterial`）にしている（下の表は両方の差し込み位置）。

| 処理           | GLSL（main）の差し込み位置                                | TSL（webgpu）の入れ先                          | 内容                                                                                                        |
| -------------- | --------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| 窓の判定と点灯 | `color_fragment` の後                                     | `colorNode`（外壁の変数を property に入れる）  | 1 タイル 4×4 窓（3.2 m × 3.5 m）。窓 ID = ベイ番号（576 m 周期で折り返す）・階・壁の向き・建物の tint       |
| ガラス         | `roughnessmap`/`metalnessmap`/`normal_fragment_maps` の後 | `roughnessNode`・`metalnessNode`・`normalNode` | 窓は roughness 0.07、カーテンウォール（office_glass）は 0.04・metalness 0.65・板ガラスごとに ±1° 程度の傾き |
| 点灯した窓     | `emissivemap_fragment` の後                               | `emissiveNode`                                 | 近くは部屋、遠くは平らな光。ガラスの反射分（Schlick、F0 0.04 / 0.2）を引く                                  |
| 地面際         | `aomap_fragment` の後                                     | 照明モデル（`ambientOcclusion` を上書き）      | 間接光を高さ 2.6 m までで最大 65 % 減、街路の谷で 20 % 減。直接光は泥はね分だけ（1 m まで 18 %）            |

毎フレーム `main.ts` の 1 行（`buildings.setFacadeClock(env.now(), env.wetness)`）で、ゲーム時刻の点灯割合（スタイル 8 種＋路面店）、濡れ具合、テレビのちらつき用の秒を uniform に入れる。webgpu ブランチではこれらは共有の render グループの uniform で、render ごとに 1 回の転送で全タイルに届く。

## 画質設定

`GRAPHICS.settings.windows`（設定 › 画質 › 夜の窓）ごとに別のシェーダーにしている。main では define と `customProgramCacheKey`、webgpu ブランチでは設定ごとに 1 つの node のグラフ（全タイルのマテリアルが共有するので、パイプラインも設定ごとに 1 つ）。切り替えると生きている外壁マテリアル全部のノードを差し替えて `needsUpdate` を立てる。

| 設定                             | define（main）       | 見え方                                                             |
| -------------------------------- | -------------------- | ------------------------------------------------------------------ |
| `flat`（単色・低の既定・スマホ） | なし                 | 元のまま。窓の 40 % が同じクリーム色（1.0, 0.78, 0.45）×1.2        |
| `lit`（点灯のばらつき・中）      | `FACADE_WINDOWS_LIT` | 時刻と用途による点灯、色温度、明るさ、ブラインド・カーテン、テレビ |
| `rooms`（部屋の奥行き・高/最高） | ＋`FACADE_INTERIOR`  | さらに 140 m 以内の点灯窓の奥に部屋                                |

濡れは `GRAPHICS.settings.wetRoads !== "off"` のときだけ（uniform を 0 にするだけなので再コンパイルなし）。ガラス・地面際・乾いた雨じみは全設定で描く。

webgpu ブランチの 3 つのグラフは、three の WGSLNodeBuilder で WGSL にして naga で検証した（影付きの太陽と環境マップあり。フラグメントは flat 1,153 行・lit 1,833 行・rooms 2,006 行）。[^wgsl-offline] 微分（`fwidth`）とテクスチャ配列の取得は分岐の外に置いている（WGSL は一様な制御フローを要求する）。部屋の箱との交差は本物の分岐の中で、点灯した近くの窓だけが計算する。

# 点灯割合（仮定）

用途はスタイルから決める: office_glass・office_concrete・office_tile = オフィス、apartment_balcony・apartment_small・brick = 住宅、mixed_use = 雑居ビル、metal_panel = 倉庫・工場。1 階は路面店（オフィス・雑居ビルと、apartment_balcony の 4 割＝下駄履き）。

| 時刻  | オフィス | 住宅 | 雑居 | 路面店 | 倉庫 |
| ----- | -------- | ---- | ---- | ------ | ---- |
| 3 時  | 0.04     | 0.05 | 0.06 | 0.10   | 0.05 |
| 9 時  | 0.85     | 0.16 | 0.60 | 0.72   | 0.80 |
| 19 時 | 0.52     | 0.70 | 0.72 | 0.90   | 0.20 |
| 21 時 | 0.30     | 0.72 | 0.60 | 0.62   | 0.08 |
| 23 時 | 0.11     | 0.43 | 0.38 | 0.24   | 0.05 |

- 土日・祝日（`ruleTime.ts` の暦）はオフィス ×0.3、倉庫 ×0.4。
- 建物ごとに ×0.45〜1.45（忙しいビルと空いたビル）。オフィスは 65 %、雑居は 50 %、路面店は 70 %、倉庫は 80 % の窓が「階ごと」の判定に従う（テナントは階単位で点ける）。住宅は窓ごと。
- **これは調べた統計ではなく仮定**。オフィスは米国の業務ビル照明スケジュール（平日 9〜17 時 0.9、夜にかけて下がる形）を記憶から当て、東京の残業で 1 時間遅らせた。住宅は「0 時前後に寝る」という一般的な生活時間の形。NHK 国民生活時間調査（睡眠の時刻別行為者率）と DOE の参照ビルのスケジュールを確かめようとしたが、検索の上限に達し、nhk.or.jp と nrel.gov は取得できなかった。総務省の社会生活基本調査 2021 の概要 PDF には時刻別の値が無かった（統計表は e-Stat の Excel）。数字を直すならそこから。

窓の判定値は TS 側 `windowPick` がシェーダーと同じ計算（Dave Hoskins の hash12 を float32 で）をしていて、テストで確かめている: 172,800 窓で 10 区間がそれぞれ期待値の ±5 % 以内、指定した割合 0.1/0.3/0.7 に ±3 % 以内で点く、オフィスの隣の窓は 72 % 前後で同じ状態（住宅は独立の 52 %）、ベイ番号を 180 ずらしても同じ（浮動原点の付け替えで点灯が変わらない）。[^facade-tests]

# 色と明るさ

色温度は黒体の線形 sRGB（最大成分で正規化）を、夜の目・カメラのように 4000 K へ 1/3 だけ白色補正した値にした。[^kelvin-calc]

| 色温度 | 黒体（線形）        | 使った値          |
| ------ | ------------------- | ----------------- |
| 2700 K | 1.000, 0.423, 0.100 | 1.0, 0.49, 0.14   |
| 3500 K | 1.000, 0.577, 0.260 | 1.0, 0.668, 0.365 |
| 4000 K | 1.000, 0.659, 0.379 | 1.0, 0.763, 0.532 |
| 5000 K | 1.000, 0.795, 0.630 | 1.0, 0.92, 0.885  |
| 6500 K | 1.000, 0.944, 0.992 | 0.72, 0.78, 1.0   |

- オフィス 4500〜6500 K、住宅は電球色（2700 K）45 %・4300〜4700 K 30 %・昼光色（6300〜6500 K）25 %（日本の住宅は天井の昼白色・昼光色が多い）、路面店 4600〜6500 K、雑居ビルは全域。
- 露出前の線形の明るさ: オフィス 2.4、住宅 1.7、雑居 2.0、路面店 3.6 に窓ごと ×0.6〜1.4。平らな窓はその 0.4 倍、部屋の天井灯は 3.2 倍（ブルームが拾う）。
- 住宅の点灯窓の 7 % はテレビだけ（青、1 秒に 2.7 回の場面転換で明るさが変わる）。
- 窓が 1 画素より小さくなる距離では（`fwidth` で判定）、点灯 0/1 と色を建物の平均に寄せる。遠くの高層ビルが点滅して見えるのを防ぐため。

## ブラインドとカーテン

テクスチャに描いてあるブラインド・カーテン（明るい色。輝度 0.16〜0.34 で判定、カーテンウォールは除く）と、シェーダーで下ろすもの（オフィスの 3 割が途中まで、住宅は 38 % が全面・22 % が途中まで、雑居の 25 % がすりガラス）は、部屋を描かず平らに光る。上ほど明るく、オフィスは 10 cm のスラット。

# 部屋（interior mapping）

van Dongen の方法: 視線をガラスの奥へ延ばし、規則的に並ぶ床・天井・壁の面と交差させて、最初に当たった面の色を出す。部屋の数は描画コストに効かない。[^van-dongen-2008]

- 箱は窓の面の座標（壁沿い = テクスチャの u と同じ世界軸、上 = 高さ、奥 = 法線の逆）。幅はオフィス 12.8 m（ワンフロア 4 ベイ）、路面店 6.4 m、住宅 3.2 m。奥行きはオフィス 9〜13 m、住宅 4.5〜6.5 m。高さ 3.5 m。
- 奥の壁は上ほど明るく、横の壁は陰、床は暗く、天井は照明の間が暗い。オフィスは 1.8 m × 2.4 m ごとの照明パネル、住宅は丸い照明 1 つ。奥行き方向に 55 % まで暗くなる。
- 窓と平行な家具の板を 1 枚（奥行きの 30〜65 %）: オフィスは机（0.75 m）とモニター、住宅はソファの背。
- 70〜140 m で平らな光に溶かす。昼は近くの点灯した部屋だけを 8 % の明るさで見せる（日中の事務所の天井灯）。

## 効かなかったこと

- 最初の調整（奥の壁 0.45〜1.0、側壁 0.38〜0.83、天井 0.55）では、トーンマッピング後に部屋がほぼ白一色になり、奥行きが読めなかった。面ごとの明るさの比を 3〜6 倍に広げて（奥の壁 0.22〜0.82、側壁 0.1〜0.42、天井 0.1）ようやく箱に見えた。
- office_concrete の窓は半分ほどテクスチャにブラインドが描いてあり、その窓は部屋が出ない。街路から見上げた接写では部屋が少なく見えた。

# 雨・濡れ

- 濡れ（`env.wetness`）で壁の拡散色を最大 32 % 暗く（金属パネルは 4 割）、roughness を 0.32 へ寄せる。ガラスは変えない。
- 雨筋: 窓台（階の下から 0.19）から 25 cm 幅の列で 0.5〜2 m 下へ。列の 45 % に出る。乾いていても 8 % 暗い雨じみ、濡れると +25 %。

# 計測

| 条件                                                     | 変更前                           | 変更後                                    |
| -------------------------------------------------------- | -------------------------------- | ----------------------------------------- |
| 描画呼び出し（建物だけ）                                 | 136（追従視点）/ 106（壁の接写） | 同じ                                      |
| 1 回の render＋readPixels の中央値（建物だけ、夜の接写） | 12.4 ms                          | 6.0〜18.6 ms（ほぼ同じシェーダーの 4 回） |

- 計時は**使えなかった**: 他のエージェントが同時に GPU を使い、load average 30〜92 の中で、同じに近いシェーダーの回ごとの差（6.0 ms と 18.6 ms）が変更前後の差より大きかった。[^session-shots]
- 推定: lit で窓ごとにハッシュ 8 回と数十の演算、rooms は 140 m 以内の点灯窓だけ箱との交差と家具の板で＋80 演算程度。テクスチャ取得は増えない。測るなら同じページで 夜の窓 を flat/lit/rooms と切り替えて比べる（切り替えは再読み込み不要）。

# 落とし穴

- 3DTilesRendererJS は破棄するマテリアルを `load-model` の前に集める。`buildings.ts` が差し替えた外壁マテリアルは集められず、破棄されていなかった。設定の切り替えでマテリアルを追う集合が漏れるので、`dispose-model` で自分で破棄するようにした。
- ヘッドレス Chrome の DevTools ポートの既定（9334）は他のエージェントの QA と衝突する。自分の検証は別ポート（9396）にした。
- 内側の角の暗がりは入れていない。隣の壁の情報がフラグメントに無く、頂点属性で持つにはタイル読み込み時の隣接計算が要る。
