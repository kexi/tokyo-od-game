# 実装したこと

- ミラーは車内を描くカメラ（near 0.02 m）の視錐台と交差する面だけを更新する。街のカメラの near を使うと、目の近くのミラーが消える。元の 3 フレームに 1 回という各ミラーの順番は残す。画面外の順番を飛ばして別のミラーを毎フレーム描くと負荷が減らないため。新しく視界に入ったミラーを優先し、1 フレームに最大 1 枚。一時停止中は更新しない。[^code]
- ナビ・TV はキャンバスを描き直したときだけ CanvasTexture の更新を要求する。TV を表示中かどうかと、画素が変わったかを分ける。TV から地図に戻るときやチャンネル変更時は間隔を待たず描く。[^code]
- `tokyoDate` の `Intl.DateTimeFormat` を再利用する。日付自体はキャッシュしないので、リプレイで過去へ戻っても入力日時に対応する。[^code]

# 計測条件と結果（2026-10-06 JST）

M2 Max、Headless Chrome 154、WebGPU / reversed depth、開発ビルド、1280×800、DPR 1、画質 ultra（影 4096、部屋あり、交通 many）。基準コミット `f70e526`、変更後は `perf/render-overhead` の未コミット差分。東京駅付近で停車、`seed=20261006`、開始指定 `35.681236,139.767125`。道路への補正後は `35.6819244558302,139.765737721292`。各条件で別の Chrome を起動し、開始後 30 秒待ち、20 秒を 3 回測った。[^measurements]

| 条件     | 変更前 FPS（3 回） | 変更後 FPS（3 回） | p95 フレーム間隔 |
| -------- | ------------------ | ------------------ | ---------------- |
| 昼・晴れ | 41.6 / 41.8 / 43.3 | 46.8 / 46.1 / 47.0 | 両方 33.4 ms     |
| 夜・雨   | 43.8 / 39.4 / 41.6 | 35.6 / 33.8 / 35.8 | 両方 33.4 ms     |

昼は速くなったが、夜は逆に遅かった。夜の変更後には 50 ms 超のフレームが各回 1 / 1 / 0 件（最大 50.1 ms）、ほかは 0 件。これは FPS の全面的な改善を証明しない。seed は固定しても非同期ロード・交通の状態は完全には揃わず、ホスト負荷も変わる。[^measurements]

最初の同一ページ比較（`validation/night-ab.json`）は 37.5 / 39.5 / 44.0 / 44.1 FPS だったが、**性能判断から除外する**。後続の測定で、HMR の時刻付き URL でロードしたモジュールと、計測側が時刻なしで import したモジュールが別になる問題を発見した。この旧スクリプトには従来方式のミラー描画回数の検証が無く、差し替えの適用を保証できない。下記では本体のインスタンスを直接切り替え、従来方式が必ず毎フレーム1枚描くことを検査した。通常プレイの変更前後の別起動計測は実コードを切り替えたもので、この差し替え問題には該当しない。[^validation]

フレームの測定とは別に、関数を計装して 6 秒測った。これらは **CPU の呼び出し時間と更新要求回数**で、GPU の実行時間や実転送回数ではない。[^measurements]

| 条件・版 | フレーム数 | ミラー描画回数 | ミラー CPU 合計 | ナビ転送要求 |
| -------- | ---------: | -------------: | --------------: | -----------: |
| 昼・前   |        262 |            262 |        1,210 ms |          262 |
| 昼・後   |        284 |            189 |          735 ms |           44 |
| 夜・前   |        257 |            257 |        1,098 ms |          257 |
| 夜・後   |        224 |            149 |          834 ms |           44 |

視界にない左ミラーの分だけ描画が約 1/3 減り、ナビの転送要求は約 7.3 回/秒になった。街の描画 CPU は昼が 11.94 → 12.21 ms/回、夜が 11.40 → 14.30 ms/回で、夜のシーン自体の負荷も揃っていない。描画回数を減らす効果と、シーン・マシンの差を区別する必要がある。

初期の CPU プロファイルでは、three r186 の材質キャッシュキー計算が目立った。影用材質の version 不一致を大量に観測したが、three 内部のキャッシュを無理に固定すると影・材質変更を壊しうるため、この変更では触っていない。GPU が律速かどうかは未測定。

## 同一シーンで描画処理を切り分けた再計測

同じページで30秒動かした後、ゲームの更新を止めて車・交通・時刻・雨の状態を固定した。描画は実時間の requestAnimationFrame で継続し、`Cockpit.render` と `FrameComposer.present` の同期 CPU 時間を測った。両方式とも同じ計装を使った。各切り替え後の2秒の描画ウォームアップを除き、各12秒、A/B/B/A/B/A/A/B の順で8回。A は全ミラーの順番更新＋毎フレームのナビ転送、B は今回の方式。日付やゲーム更新の時間はこの描画 CPU 時間に含めない。[^fixed-scene]

| 条件     | Aの描画CPU平均 | Bの描画CPU平均 | 削減 | A / B のFPS平均 |
| -------- | -------------: | -------------: | ---: | --------------: |
| 昼・晴れ | 15.74 ms/frame | 14.87 ms/frame | 5.6% |   59.92 / 59.96 |
| 夜・雨   | 16.10 ms/frame | 14.81 ms/frame | 8.0% |   59.17 / 59.98 |

CPU平均は各12秒の平均を4回分平均した値。隣接するA/Bの4組すべてで、昼夜ともBのCPU時間が短かった。ナビ転送要求は約60→7.49回/秒、ミラーは1→約0.667回/frame。夜Aで50 ms超のフレームが1回、ほかは0回。例外ログは両方0件。シーンの全物体のID・可視状態・位置・回転・倍率から作ったハッシュを各測定の前後で照合し、8回を通じて夜2,846個・昼2,856個の状態が不変だった。[^fixed-scene]

**同じ描画内容でCPU負荷が減ることは確認できた。** この固定試験は物理・AI・道路ロード等のゲーム更新を含まず、FPSはほぼ60の上限に達している。GPU実行時間も測っていない。通常プレイのFPSが同じ割合で伸びるという意味ではなく、通常プレイは次の追加試験で切り分けた。

`tokyoDate` も同じブラウザで、異なる1,000日を入力し、旧版（毎回formatter生成）と新版を同じ8回の順序で比較した。1,000回あたり昼32.37→1.88 ms、夜32.80→1.97 ms。全日付の出力JSONが一致した。これは単独の処理時間で、ゲーム全体が約17倍速くなるという意味ではない。[^fixed-scene]

## 夜・雨の通常プレイでの追加比較

固定試験と同じ機器・画質でゲームを30秒動かし、今度はゲーム更新を止めず、交通・雨・時計を進めたまま東京駅付近で停車して測った。スマホも通常どおり表示した。A/B/B/A/B/A/A/B の順に、各切り替え後2秒待ってから20秒ずつ測定。Aは本体のミラー更新インスタンスを直接差し替え、ナビの変更時転送を抑えたうえで毎フレーム1回転送する。Bは実装どおり。Aのミラー描画数と転送要求が実フレーム数と一致することを毎回検査した。[^live-night]

| 指標（各方式4回の平均）       |    従来A |  改善後B |    変化 |
| ----------------------------- | -------: | -------: | ------: |
| FPS                           |    35.89 |    38.70 |  7.8%増 |
| ゲームのメインフレームCPU時間 | 27.44 ms | 25.38 ms |  7.5%減 |
| Cockpit.renderのCPU時間       | 20.80 ms | 19.27 ms |  7.4%減 |
| ミラー描画／フレーム          |        1 |    0.667 | 約1/3減 |
| ナビ転送要求／秒              |    35.94 |     7.18 | 約80%減 |

各回のFPSは順に `A 36.09 / B 39.39 / B 37.49 / A 33.37 / B 39.44 / A 36.02 / A 38.09 / B 38.49`。隣接する4組すべてでBのFPSが高く、メインフレームCPU時間も短かった。p95フレーム間隔は全回33.4 msのまま。50 ms超はAが合計4回（最大116.6 ms）、Bは0回だったが、単発の長いフレームの原因までは特定していない。例外ログは0件。

この結果は、**今回の地点・同一セッションでは通常プレイの夜雨でも改善した**という根拠になる。シーンの物体数は2,950→3,103へ変化しており、交通や非同期ロードを完全に揃えた試験ではない。先の別起動比較の悪化を全環境で否定するものでもない。A/Bはミラーとナビの更新方法を戻した比較で、日付処理の再利用やミラーを描く呼び出し位置は両方とも現在の実装。走行中の道路再構築、事故、端末内AI同時実行はこの結果に含まない。固定試験と通常プレイで計測区間も異なり、固定は `Cockpit.render + present`、通常プレイの描画欄は `Cockpit.render` のみなので、そのCPU値同士を直接比較しない。[^live-night]

## 再計測

1. `just serve-dev` で開発サーバーを起動する。
2. `just measure-perf before` / `just measure-perf after` を各版で実行する。`QA_URL` で URL を変更できる。直接呼ぶ場合は `node scripts/qa/perf.mjs --label sample --seconds 20 --runs 3 --warmup 30`。
3. `.qa/perf/<UTC 日時>-<label>/report.json` と昼夜の画像を比較する。版・差分・実際の設定・位置・OS・ホスト負荷・例外ログも記録される。

固定シーンでの比較は `just measure-perf-fixed`（または `node scripts/qa/perf-fixed-scene.mjs --seconds 12`）。`.qa/perf/<UTC 日時>-fixed/report.json` に各回のCPU時間・フレーム時間・更新回数・シーンのハッシュ・日付比較を残す。スクリプトは本体の描画関数とミラー更新インスタンスに依存するので、変更時には停止状態・従来方式の毎フレーム更新・シーン不変の検査を省かない。

夜雨の通常プレイは `just measure-perf-night`（`node scripts/qa/perf-fixed-scene.mjs --live --seconds 20`）。`.qa/perf/<UTC 日時>-live-night/report.json` に保存する。全ゲームフレームの計装は `main.ts` の `tick` コールバックを識別し、車内描画の回数と計装したフレーム数が一致することを検査する。

仮想時間は使わない。計測中にビルド・テスト・HMR を走らせない。CPU 詳細の影診断だけは three r186 の内部 API に依存するので、three 更新時には見直す。今回の FPS はヘッドレス環境の参考値であり、通常のブラウザやスマホの値ではない。

# Web Worker を検討した結果

この節は描画PR時点の試作記録。後続の [道路網・規制の Worker 化](road-network-worker.md) で本番実装と実測を行った。計算単体の停止は減ったが、路面再生成の停止が別に残っている。

既に写真の現像・JPEG 化（`darkroom.worker.ts`）、音声合成（`tts.worker.ts`）、Draco 解凍（同時 2 Worker まで）は別スレッドで処理している。追加候補として、走行中の道路再構築で呼ぶ `applyRegulations` を実データで試した。[^validation]

**道路規制の対応付けが次の有力候補。** 読み込み済み道路網の 1,189 区間の `segment.line`、規制、原点を送信した（JSON 換算 776,323 bytes）。元の未分割 roadLines を再現したものではない。常駐 module Worker を先に読み込み、道路網を再構築して規制を適用し、道路網と適用結果を丸ごと構造化複製で返した。3 回の結果：

| 処理                                   | メインスレッド | Worker 試作     |
| -------------------------------------- | -------------- | --------------- |
| 道路グラフ構築                         | 1.8〜2.2 ms    | 1.9〜3.0 ms     |
| 規制の対応付け                         | 99.5〜121.1 ms | 104.9〜131.5 ms |
| メイン側 postMessage                   | —              | 1.0〜1.1 ms     |
| 送信から返却まで（複製・待ち時間込み） | —              | 138.0〜169.6 ms |

返却された `graph.segments` の JSON はメインの結果と 3 回とも一致した。ただし、返却後の `graph.nearest` は関数ではなくなった。構造化複製ではクラスのメソッド・プロトタイプが残らない。これは実装にそのまま差し込める状態ではなく、**今回 Worker の本番追加はしていない**。[^clone]

実装するなら、区間 ID を使う返却形式とメイン側のクラス・参照関係の復元、移動・原点変更後に古い結果を捨てる世代管理が必要。結果待ちの間は現在の道路網を維持し、完成したものを一度に差し替える。受信側の複製・復元時間や、道路の描画メッシュ・物理コライダーを作る時間は別に測る必要がある。Worker の総所要時間は短くならなくても、約 100 ms の同期処理をメインスレッドから外せる可能性がある。

同じ道路網で経路探索は 30 件、各 0.3〜3.1 ms（29 件成功、1 件経路なし）。今回の地点では規制適用より優先度が低い。描画全体を OffscreenCanvas に移す案は、シーンの所有権、DOM、入力、音声、画像の読み戻しまで境界を整理する大きな変更になる。`renderer.render` だけを別 Worker に送る変更では済まない。[^offscreen]

# 振る舞いの検証

- ユニットテスト：WebGL / WebGPU の座標系・通常/逆転深度、近距離・画面端のミラー、再登場・車内復帰、更新頻度、TV の更新間隔・地図復帰・チャンネル変更、JST の日跨ぎ・年跨ぎ・うるう日・時刻の巻き戻し。[^tests]
- Chrome で前・左・右・ルームミラー・前へ戻る視線を切り替え、対象ミラーの再描画と各フレーム最大 1 回を確認。TV と地図復帰も画像確認。`uncaught_error` は 0 件。[^validation]
- 最初の信号無視の写真ポストを起こし、写真が完成したことを確認。違反処理 2.7 ms、写真描画 4.0 ms、後続 7 秒の 341 フレームに 50 ms 超は 0 件（最長 33.4 ms）。単一地点・単一ケースの確認であり、事故・複数目撃者・端末内 AI 同時実行は保証しない。[^validation]
- 全テスト 890 件を確認。通常の実行ではローカルサーバーの listen が sandbox で拒否された `logSink` の 2 件だけ失敗し、同ファイルを権限付きで再実行して 10 件すべて通過。型チェック、lint、production build も通過。ビルドには従来の大きな chunk と `new URL` の警告が残る。
