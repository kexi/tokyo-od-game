# 何のための値か

性能 PR スタック（#5〜#33）を main（48dc699）に 1 本ずつ作り直す前の、main の値。各 PR の「マージ後の条件」（シナリオごとの最長フレームとメモリが、ここで決めたばらつきの幅を超えて悪くならない）と、measure-first の PR を作るかどうかの判定に使う。10 月の数値は持ち込まない。[^plan]

条件はすべて: ヘッドレス Chrome 157、M2 Max、WebGPU、1280×720 前後。ヘッドレスはフレームが 16.7 ms 刻みに出るので、最長フレームは 50.0 / 66.7 / 83.4 … のどれかになる。ほかの担当の計測と同じ機械で走らせた（鍵で 1 本ずつだが、生成や型検査は重なりうる）。[^runs]

読み:

- 最長の 466〜567 ms のフレームは、どちらのシーンも影のパスの中のノードの組み立て（影のシェーダー）で 400 ms 前後。three の `build` の自己時間が最大。
- **どの材質の影か: 外壁（#9）が第一の候補**。最長の 3 フレームで、影のパスかつノードの組み立ての中に出るゲームの関数は、`world/facade.ts` の無名の関数（新地域 32 ms・連続ワープ 49 ms）、`render/shaderMath.ts` の `hash12`・`byIndex`、`world/facade.ts` の `lampColour`（外壁の窓の色の TSL）。three r186 は影のパスで材質の `colorNode` を影の材質に写す（`Renderer._getShadowNodes`）ので、外壁の色の段まで影のシェーダーに組み立てている見込み。無名の関数が `surface()` の `Fn` だというのは推定（配信される JS の行はソースの行と 1 対 1 でない）で、根拠は名前のある `lampColour` などに置く。残りの約 380 ms は three の内部。新地域ワープでのパイプラインの種類分けは未確認（下のパイプラインの節は昼晴れの走り出しの値で、そこでは InstancedMesh の影が多い）。[^review]
- 新地域の 50 ms 超のフレームは、1 フレームあたり 70 ms ほどで、その大半は描画そのもの（render/frame.ts の下に 10.1 s、cockpit.ts 1.8 s、water.ts の映り込み 1.1 s）。
- 人の生成と動き（#33）の自己時間は、計測区間の 0.15 %（新地域）・0.10 %（連続ワープ）。計画の線（1 % 未満なら入れない）より小さい。
- 経路探索の 147 ms は、新地域の 1 フレームで自動運転の経路を作り直した所（navigation.ts の search・planRoute）。
- **50 ms の線の頑健さ**: ヘッドレスのフレームは 50.0 / 50.1 に出るので、3 vsync のフレームが「50 ms 超」に入るかは揺れで決まる。60 ms 超に絞っても（新地域 206・連続ワープ 18 フレーム）、上位 5 件の顔ぶれは同じ（新地域: 影・ノード・getMaterialCacheKey・updateMatrixWorld・近傍検索、連続ワープ: ノード・影・コライダー・getMaterialCacheKey と、GC を除けば地形のチャンク／含めれば GC）。
- 道路の返信: listener の自己時間（`roadNetworkBuilder.ts` の message の listener、すぐ上が `(root)`）は `event.data` を読む所で、その大半は構造化複製の復元と読む（見込み。エンジンが listener に取り込んだ `finish` の分とは分けていない）。

# 判定の定義（2026-11-24 にコーディネーターが決め、2026-11-28 にレビューで線を置き直した）

マージ後の条件（バッチごとに main で基準を 2 本取り直す）は、次で判定する。[^plan]

- **最長フレームの悪化**: シナリオごとに、取り直した 2 本の最長の大きい方が、基準 2 本の最大 + 25 ms（16.7 ms の段の中間）を超えたら悪化。線は 新地域 558.3 ms、連続ワープ 641.6 ms、原点変更 108.4 ms、通常 75.1 ms、道路更新 91.6 ms。1 段上（+16.7 ms）は悪化に数えず、2 段上（+33.4 ms）は悪化。段の上の値は同じ段でも ±0.1 ms 揺れる（50.0 / 50.1、616.6 / 516.6）ので、線を段の上に置かない。
- **メモリの増え**: 東京駅 far（`--time-parse` なし）の GC 後のヒープと配列の実体が、基準 2 本の最大（80 / 514 MB）の +2 %（81.6 / 524.3 MB）を超えたら増えた。値は整数 MB で出るので、**ヒープ 82 MB 以上・配列の実体 525 MB 以上で増えた**。
- **50 ms 超の回数は判定に使わない**: 1 本の中でも 2 倍ほど揺れる（新地域 130〜238）。
- 受け入れの基準は「部品の改善 + 全体の悪化なし」（計画の 4 章の部品の条件を満たし、上の線を超えない）。

# 確かめていないこと

- ばらつきの幅を 2 本で決めた。新地域・連続ワープの最長は 2 本で 67〜100 ms 違う。マージ後の判定で幅の外に出たら、取り直しの 3 本目で確かめる。
- 帰属は 1 本。候補の順位は 1 本の値で、プロファイラを掛けた分だけ遅い（新地域の最長 566.6 ms は、掛けない基準の 466.7〜533.3 ms より長い）。
- 影のパスで組み立てているのがどの材質か（新地域の 400 ms 前後のフレーム）。外壁が第一の候補だが、種類分けは新地域のワープでは取っていない。#19・#24 を決めるときは、本数だけでなく 1 本の組み立ての時間も見る（本数の線は、1 本が約 400 ms でも通ってしまう）。
- 直した候補（`__qaParseTile`、返信の listener）は、保存したプロファイルで数え直しただけで、このときは道具をブラウザで走らせ直していなかった（その後の 1 本は上の「直した道具の確かめ」）。**次の 1 本の tileParseSync は表より広い**: `__qaParseTile` の中は parse の同期の部分全体（b3dm の頭・2 つの表・glTF の JSON の部分）なので、表の 377 ms とは比べず、同期の部分全体どうしで比べる（参考: 保存したプロファイルで `parseTile` の枠の下は新地域 425 ms。await の後に再開した分も入るので上限）。数え直しの #10 は束ねた版の縮めた名前（`Q$1`・`$$1`）で当てた 1 回だけの値で、道具には入れていない（版が変わると黙って外れるため）。
- 開発サーバーの値（束ねていないモジュール）。公開の版では関数名が読めないため、帰属はこの版でしか取れない。
