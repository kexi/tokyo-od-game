# 何を選ぶ設定か

設定 › 画質 › シェーダーの事前作成。

- **先に作る**（既定）: 街が読めた後、読み込み画面が「描画の準備中（シェーダーを作成）…」の間、`main.ts` の `precompile` を待つ。`precompile` が作るのは、街の 4 方向、後から出る車と人（見本を置いて `compileAsync`）、運転席とガラス、描画の各パス、目撃者のスマホと写真（`prewarmWitnesses`、暗室ワーカーの起動を含む）。終わると `pipelines_compiled`（`durationMs`）を書く。
- **作らない**: `precompile` を呼ばず、そのまま「始められる」に進む。`pipelines_skipped` を 1 行書く。それぞれの材質のパイプラインは、初めて描くフレームで作られる。
- 対象外: 裏で進む準備（`buildings.ts` の遠景の外壁、`farGround.ts`）。どちらも待たせずに作り、できるまで物を隠しているだけなので、切っても待ち時間は変わらない。開発の版の `?noprewarm`（目撃者の分だけ外す）は別のまま残した。[^code]

扱い:

- 既定は PC もスマホも「先に作る」。`SHADER_PREBUILD_DEFAULT` 1 つで変えられる。
- プリセット（最高〜低）はこの項目を変えない（描画方式と同じ）。プリセットの外の項目は `NON_PRESET` の鍵から拾う。以前は `withPreset` が `{ backend: from.backend }` と 1 つずつ書いていたので、2 つ目の項目はプリセットのたびに戻るところだった。テストが「`inPreset: false` の行 = `NON_PRESET` の鍵」を確かめる。
- 次の読み込みから効く（`onReload`）。読み込みのときに 1 回だけ走る物なので、途中で替えてもやることが無い。途中で「先に作る」に替えた瞬間に全部を作るのは、そこで長く止まる。
- 保存は画質と同じ `tod.graphics`。この項目の無い古い保存は「先に作る」で読む。[^tests]

# 計測（on と off）

ヘッドレス Chrome（M2 Max、WebGPU）。ヘッドレスはフレームが 16.7 ms 刻みになる。`--mobile` は UA を Android にして低の画質にするだけで、スマホの GPU ではない。[^measure]

- 読み込み: 平均で PC 12.86 → 11.79 s（−1.08 s）、スマホ 6.52 → 5.19 s（−1.33 s）。precompile そのものは PC 0.89〜0.99 s、スマホの設定 0.47 s。閉じる時刻は建物の読み込みで 1 s 前後ばらつくので、縮む量は precompile の時間で見るのが確か。

- 30 秒に作ったパイプラインは、off で PC +17〜21、スマホ +7〜9 本。

## 初めて出る物の瞬間（前後 1 秒のいちばん長い間隔 / その間に作ったパイプライン）

| 設定       | 運転席（start）    | 最初の違反（写真のポスト） | 最初の雨        |
| ---------- | ------------------ | -------------------------- | --------------- |
| PC on      | 283 / 50、333 / 62 | 33 / 0、33 / 0             | 33 / 3、83 / 3  |
| PC off     | 500 / 18、533 / 18 | 67 / 7、67 / 7             | 283 / 4、50 / 4 |
| スマホ on  | 333 / 45、283 / 43 | 17 / 0、17 / 0             | 17 / 1、17 / 1  |
| スマホ off | 350 / 10、350 / 11 | 33 / 6、17 / 5             | 17 / 1、17 / 1  |

- 違反: on は目撃者のスマホと写真のパイプラインを 1 本も作らない（precompile が済ませている）。off は 5〜7 本作り、PC で 33 → 67 ms。
- 雨: PC off の 1 回だけ 283 ms。もう 1 回は 50 ms で、2 回ではばらつきと分けられない。スマホの設定（低）はフロントガラスの雨粒が切ってあり、差が無い。
- 崩れ: off の 4 回の画面（運転席・違反の後・雨）に、物が出ない・黒く出る・運転席や雨のガラスが描かれないといった崩れは無かった（PC の雨の画面にガラスの雨粒、違反の後に写真つきのポスト）。

## 見つけたこと: on でも走り出しに作っている

on でも、始めた前後 1 秒に PC で 50〜62 本、スマホの設定で 43〜45 本のパイプラインを作っている。off はその 1 秒に 10〜18 本（読み込み画面の間、タイトルの視点で街の分を 31〜59 本作っている）。precompile の見本や視点では鍵が合わず、運転席に入った最初のフレームで作り直している物があると読める。どの材質かは調べていない。走り出しのいちばん長い間隔（on でも 283〜333 ms）の大半はここにあり、precompile の対象を見直せば on の走り出しも縮む見込み。

# M1 の控えを捨てる変更との関係

`precompile` が見本として置く車・人・スマホの控えは作った後も残り、その材質のパイプラインを生かしている（memory-growth.md、M1 の (a)）。off では見本が無く、車や人の最後の 1 台が居なくなるたびにパイプラインが捨てられ、次に現れたときに作り直すと読んだ。往復 10 分で比べた。[^roundtrip]

| 設定 | パイプラインの数（10 s → 606 s） | 1 分あたり | 10 秒ごとの最長フレームの最大 | 最長が 250 ms を超えた 10 秒 |
| ---- | -------------------------------- | ---------- | ----------------------------- | ---------------------------- |
| on   | 101 → 770                        | 67.3       | 467 ms                        | 60 のうち 18                 |
| off  | 114 → 803                        | 69.2       | 467 ms                        | 60 のうち 6                  |

- 作り直しの速さは on 67.3・off 69.2 本/分で、ほぼ同じ。読みで心配した「見本が無いと作り直しが増える」は、この 1 回ずつでは +3 % ほどで、はっきりした差は出なかった。10 秒ごとの p95 の中央値は on 33 ms・off 50 ms、最長が 250 ms を超えた 10 秒は on 18・off 6 で、向きがそろわない（ばらつきの内）。
- この往復はワープで建物を読み直すので、どちらも 10 秒ごとの最長は大きい。1 回ずつなので、差は傾向として読む。
- 開発サーバー・視界 far での数で、memory-growth.md の QA の版の数（1 分あたり 37〜44）とは条件が違う。

# 確かめていないこと

- 往復の差。1 回ずつなので、+3 % が本当の差かどうかは分からない。
- 本物のスマホ（Pixel 11 Pro・iPhone）での precompile の時間と、off の走り出し。PC の Chrome の UA を替えただけで、GPU とシェーダーのコンパイラは M2 Max のまま。
- 夜・雨から始めたときの差（始める天気と時刻は昼晴れに固定した）。
- on でも走り出しに作り直している材質の正体。
- 窓のある Chrome（GPU がフレームを刻む）での差。ヘッドレスは 16.7 ms 刻み。
